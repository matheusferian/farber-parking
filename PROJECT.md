## Project Overview

**Makers Air Valet** (branded **Ascend Valet** for private-flight check-ins) is a single-page web application that runs the day-to-day valet parking operation for Makers Air, operated by Farber Parking, at a private aviation terminal (FBO). It replaces paper logs with a live system of record for every vehicle in custody.

Core purpose: **never lose, misplace, or misdeliver a vehicle.** The system tracks:
- Passenger/vehicle check-in and check-out (delivery)
- Vehicle location (hangar) at all times
- Expected return dates, including unconfirmed/approximate dates that need follow-up
- Delivery via three channels: Normal (in person), Customs, or Lockbox
- Communication with passengers via prefilled SMS (welcome, confirmation, Customs welcome-back, gratuity)
- Physical ticket printing (customer copy, key tag, dashboard tag, flight tag) via a networked Epson ePOS printer
- Daily cash/card/digital-payment closing reconciliation
- Monthly operational reporting for staffing and management

Primary users are on-site valet attendants working from iPads during live operations, plus a supervisor role that reviews reports and closings.

## Technology Stack

- **Frontend:** Single-file vanilla HTML/CSS/JS application — [index.html](index.html) (~5,800 lines: markup + inline `<script>`/styles combined with [styles.css](styles.css)). No build step, no framework, no bundler.
- **Language:** JavaScript (ES5-leaning style, `var`-based, some `async/await`), HTML5, CSS3.
- **Shared JS helpers:** [utils.js](utils.js) — XSS-escaping, date parsing/formatting, phone formatting, fuzzy name matching.
- **Fonts:** `DM Sans` (body), `Syne` (display/numeric emphasis), `DM Mono` (tags/badges).
- **Icons:** Font Awesome (`fa-solid`/`fa-regular`) for tab icons; emoji used extensively elsewhere in the UI for status/section markers.
- **Database:** Supabase (managed Postgres + REST API + Row Level Security). Accessed directly from the browser.
- **Printing:** Epson ePOS thermal printer over the local network (default IP `10.20.60.142`, reachable via `setPrinterHost()` from the browser console if it changes). Printer protocol switched from `https://` to `http://` (see Changelog).
- **Hosting:** GitHub Pages, static file hosting, no server-side runtime beyond Supabase — see Deployment section below for the full setup.
- **External services:**
  - Supabase (database, auth, RLS)
  - Device-native SMS/Messages app (system opens `sms:` links — the app never sends SMS itself)
  - Device-native Phone app (`tel:` links)
  - Stripe payment link (gratuity collection) — `https://buy.stripe.com/8x214mccK0uh9TjgIM6Vq00`
  - iOS Contacts import via generated `.vcf` files

```

```

**Production verification procedure** (run after every push, not assumed from a successful push):
1. Poll `GET /repos/matheusferian/farber-parking/pages/builds/latest` (via `gh api`) until `status` leaves `"building"`; confirm `status: "built"` and the `commit` field matches the pushed SHA.

3. Fetch `styles.css` and `utils.js` directly → confirm `HTTP 200` on each.

5. Load `?mode=tv` → confirm it loads cleanly (it will show the login overlay, by design — TV Mode only activates after a real sign-in).
6. Spot-check that the specific change just shipped is actually present in the live file content (e.g. `curl` + `grep` for a marker string/constant unique to that change) — never assume the deploy contains what was intended just because the build succeeded.

## Database

Supabase/Postgres. Two known tables (schema for `passengers` is inferred from application code — no migration file defines its original creation, so it predates the tracked migrations).

### `passengers` (primary operational table)

**Purpose:** One row per vehicle check-in ("trip"). A returning passenger who checks in again gets a new row (this is how "frequent passenger" visit history and per-trip Customs communication flags stay scoped correctly).

**Important fields** (as referenced throughout `index.html`):
| Field | Purpose |
|---|---|
| `name` | Passenger full name (stored upper-case) |
| `phone` | Passenger phone (formatted `(XXX) XXX-XXXX` in UI) |
| `ticket` | Unique service ticket number. Format `MMDD-N` (Makers Air) or `A-MMDD-N` (Ascend, see [[ascend-valet]]) |
| `vehicle` / car model, `color` | Vehicle description |
| `location` | Hangar code: `HANGAR 19`, `HANGAR 18`, `HANGAR 16`, `HANGAR 7`, `HH` |
| `status` | `PENDING` \| `NO DATE` \| `DELIVERED` \| `ARCHIVED` |
| `return_date` (Return) | Expected return date; required when status is `PENDING` |
| `estimated_return_date` | Approximate date when status is `NO DATE`; drives the Tasks queue |
| `checkin_date` / `checkout_date` | Timestamps used by operational reporting |
| `deldate` | Delivery date, set on delivery |
| `delivery_type` | `NORMAL` \| `CUSTOMS` \| `LOCKBOX` |
| `customer_rating` | **Retired 2026-07-13.** `GREAT` \| `NORMAL` \| `DIFFICULT`. No longer written or displayed anywhere in the live app — kept purely to preserve historical data (see [[tip-status-replaces-rating]]). |
| `tip_received` | `true` \| `false` \| `null` (not recorded). Replaces `customer_rating` as of 2026-07-13; set at delivery time via the Tip Received? modal. Added by migration `20260713_add_tip_received_column.sql`. |
| `obs` | Free-text notes (upper-cased); system auto-appends tags like `EARLY RETURN`, `APPROX DATE` |
| `not_returning` | Boolean — passenger stated they won't return with Makers Air |
| `return_flight`, `departure_time` | Return flight number and departure time, used for Flight Tag printing/sorting |
| `archived_by`, `archived_at` | Set when a record is archived |
| `welcome_back_sent_at` | Hangar 19 "Welcome Back" SMS status (separate from Customs communication flags below) |
| `customs_welcome_sent`, `customs_welcome_sent_at` | Customs Welcome-Back SMS status (added by migration `20260712_add_customs_communication_fields.sql`) |
| `customs_gratuity_sent`, `customs_gratuity_sent_at`, `customs_gratuity_dismissed` | Customs gratuity-reminder workflow state (same migration) |

**Relationships:** No foreign keys — `passengers` is a flat, self-contained operational table. "Frequent passenger" detection is done by fuzzy-matching name/phone across existing rows in application code, not via a relational key.

### `daily_closing_reports`

**Purpose:** End-of-day cash/operational reconciliation, independent of passenger PII (explicitly documented in the migration as read-only against `passengers`, no customer data stored here).

**Important fields:**
| Field | Purpose |
|---|---|
| `report_date` | One row per calendar date (`unique`) |
| `first_ticket`, `last_ticket` | Auto-computed ticket range for the day |
| `total_cars`, `checked_in_today`, `delivered_today` | Auto-computed counts (recalculable, editable pre-finalization) |
| `cash`, `card`, `venmo`, `cash_app`, `zelle` | Payment totals by method (all `numeric(10,2)`, non-negative) |
| `attendants` (jsonb) | Array of `{name, time_in, time_out}` |
| `money_pickups` (jsonb) | Array of `{value, name}` — cash pickups during the shift |
| `money_left` | Cash left on-site |
| `delivered_verified`, `hangars_verified` | Manual checklist confirmations |
| `status` | `DRAFT` \| `FINALIZED` |
| `finalized_at`, `finalized_by`, `created_by` | Audit trail |

**Business-rule constraints enforced at the database level:**
- All monetary/count fields must be non-negative (`dcr_no_negative_totals`).
- A report can only move to `FINALIZED` if both `delivered_verified` and `hangars_verified` are true (`dcr_finalized_requires_checklist`).
- **A `FINALIZED` report can never be flipped back to `DRAFT`** — enforced by a database trigger (`dcr_block_unfinalize`), not just app logic, so this holds even from the Supabase SQL editor or another client.
- No delete policy exists — closing reports (draft or finalized) are never removed through the app.
- Row Level Security: any `authenticated` user can select/insert/update; no anonymous access; no delete for anyone.

**Relationships:** None (flat table, keyed by `report_date`).

## Business Rules

- **Ticket numbering:** Auto-suggested as `MMDD-N` for the current date (e.g., `0622-1`, `0622-2`); editable, and duplicates are warned about but not hard-blocked. See [[ascend-valet]] for the `A-MMDD-N` variant.
- **Delivery workflow:** Three delivery types — **Normal** (in-person), **Customs** (vehicle staged, never released before Customs clears the passenger), **Lockbox** (key deposited, passenger notified with access instructions). Delivering (any type) always requires answering the tip question (Yes/No) — see [[tip-status-replaces-rating]].
- **Tip status (replaces Passenger Rating, 2026-07-13):** At delivery, the attendant answers a simple Yes/No — "Did the passenger leave a tip?" — instead of the old Great/Normal/Difficult rating. Stored as `tip_received` (`true`/`false`/`null`). The old `customer_rating` field and its historical values are preserved but no longer written or shown anywhere. After a successful save: Customs deliveries keep their existing Welcome Back → Gratuity SMS sequence untouched (no duplicate ask); Normal and Lockbox deliveries open a new post-delivery SMS whose copy depends on the Yes/No answer (see SMS Templates below).
  - **Confirmed live in production (2026-07-13):** End-to-end tested against the live Supabase database with a disposable `ZZTEST DO NOT USE` record (created and deleted within the same session). Verified: Yes saves `tip_received = true` and opens the no-Stripe-link SMS; No saves `tip_received = false` (correctly distinct from `null`) and opens the SMS with the exact Stripe link; Cancel changes nothing; reopening the passenger shows the correct saved status; the app's own `undoDeliverToday` safely reset the test record between passes; zero console errors throughout.
  - **Customs exclusion rule, confirmed live:** Delivering the same test record via Customs recorded `tip_received` normally but fired **zero** tip-SMS calls — the existing Customs Welcome Back/Gratuity modal opened instead, exactly as designed. This is intentional: Customs already has its own gratuity ask, so the new tip SMS is scoped to Normal/Lockbox deliveries only.
  - **Not yet validated:** physical iPhone/iPad rendering and touch interaction for the tip modal, and real on-device SMS composer behavior (Messages app hand-off) — all live testing so far has been through a desktop browser preview against the real database, not a physical iOS device.
- **Customer status lifecycle:** `PENDING` → `DELIVERED`, or `PENDING`/`NO DATE` → `ARCHIVED`. `NO DATE` requires an `estimated_return_date` to generate a Tasks confirmation item. Return Date is mandatory only for `PENDING`.
- **Customs communication flow ("Welcome Back" → "Gratuity"):** Strictly sequential — the gratuity reminder is only eligible once `customs_welcome_sent` is true; it never fires before Welcome Back, and never re-fires once sent or explicitly dismissed. This is a separate flag set from the unrelated Hangar 19 "Welcome Back" feature — the two must not be conflated in code changes.
- **Ascend Valet ("ASCEND" sub-brand):** Detected purely by ticket prefix — any ticket matching `^A-` is treated as an Ascend record (`isAscend(r)`), which changes: brand name on tickets/SMS ("Ascend Valet" vs. "Makers Air Valet"), print header ("PRIVATE FLIGHT"), badge styling, and suppresses the Hangar 19 Welcome Back feature entirely (Ascend has its own Customs-based Welcome Back/Gratuity copy instead). ASCEND check-ins are flagged as normally not needing a customer copy print (confirmation prompt shown if attempted).
- **Lockbox:** Used only when the passenger cannot be present; requires confirming the Lockbox number/instructions before depositing the key.
- **"Not Returning with Makers Air":** A checkbox at check-in that prints a warning on the customer ticket and adjusts the Welcome SMS copy; purely informational, no workflow gating.
- **Archive:** Never a hard delete — moves records out of default filters/views. Requires a 3-step confirmation (count → archiver name → final confirm). A Debug-tab bulk action exists to archive all pending 2025 records.
- **Reminders:** "Forgot Yesterday" (Dashboard) surfaces any record whose return date was yesterday and is still not `DELIVERED` — must be checked first thing every shift. The Customs gratuity reminder (see above) is a second, independent reminder system with its own eligibility rules.
- **Reports:** See the dedicated Reports section below.
- **Early Return:** When a passenger returns before their scheduled date, a dedicated action sets return date to today, status to `DELIVERED`, appends `EARLY RETURN` to `obs`, and logs it — this history then triggers a "heads up" warning on the passenger's *next* check-in.

Buttons per card: `✓ Deliver`, `Customs`, `🔒 Lockbox`, and a print icon for the individual Flight Tag. Clicking a card opens the full passenger panel.

**Quick H19 (2026-08-24, relocated same day, scoped to Leaving Today/Tomorrow later the same day):** a `→ H19` button in each card's normal quick-action row (`.dc-qd`, alongside `Deliver`/`Customs`/`Lockbox`), same `.qd-btn` size (32px) so it reads as a real action rather than a hidden detail — moved here from an earlier, easy-to-miss placement in the card's top-right meta corner (tiny 18px pill next to the ticket number) after review found it too subtle to notice on the real Dashboard. **Shown only on Leaving Today and Leaving Tomorrow** — `mkCards()` is shared across five Dashboard sections (Arrived Today, Leaving Today, Leaving Tomorrow, Sunday, Forgot Yesterday), so a new `showQuickH19` parameter is passed explicitly by each caller (`true` only for the Leaving Today/Tomorrow call sites) rather than inferred from a passenger's return date inside the shared function — Arrived Today/Sunday/Forgot Yesterday never receive it, regardless of a passenger's state. Within an eligible section, still only when the vehicle is active (not `DELIVERED`), not already at Hangar 19, and not a pending offline record. Deliberately **not** a parallel implementation — `quickMoveH19(id)` is a one-line confirm (`Move <name> to Hangar 19?`) in front of the exact same `moveHangar(id,'HANGAR 19')` the full Move Hangar workflow already uses. Double-submission protection is structural: native `window.confirm()` blocks the event loop, and `moveHangar()`'s already-there guard catches any leftover second call once it unblocks.

**Leaving Today header layout fix (2026-08-24):** `Print All` and `→ All H19` are now wrapped in one `.dt-action-group` flex container instead of being two separate sibling buttons — the header row is `display:flex; justify-content:space-between`, and with three direct children `space-between` was distributing them start/middle/end, stranding `Print All` in the center of the row. Grouping them into a single right-side flex item (mirroring the pattern Leaving Tomorrow's header already used for its own multi-button toolbar) restores the intended `[title] ... [Print All] [All H19]` layout, with `flex-wrap:wrap` on the row so the whole action pair drops to its own line together at narrow widths rather than the two buttons splitting apart from each other.

**Shared move core:** `moveHangarCore(r, hangar, note)` — the id-lookup/offline-guard/`sbUpdate`/Activity-Log/Vehicle-Location-History logic, no `confirm()`, no `showMsg()`, no `render()`. Both `moveHangar(id, hangar)` (the full workflow — confirm, toast, render, optional print-tag prompt — unchanged UX) and the new **Bulk H19** below call this one function; neither duplicates it.

**Bulk H19 — Leaving Today (2026-08-24):** a `→ All H19` button in the Leaving Today section header, next to the existing `🖨 Print All` (same `.fb-print-all-btn` toolbar style, distinct light-blue tint). Deliberately separate from the existing generic checkbox-multi-select "🚗 Move Hangar" bulk action (`bulkMoveLoc()`) — that one moves whatever's manually selected to any hangar; this one is a one-tap shortcut for "we already physically walked today's returning cars to Hangar 19, now update AirValet," auto-scoped to `isToday(r.ret) && status!=='ARCHIVED'` (the same rule that builds the Leaving Today list itself) further filtered to exclude `DELIVERED` (which by construction excludes Customs deliveries too, since those always set `status='DELIVERED'`), already-H19, and pending-offline records. One upfront confirm shows the count and a short name/ticket preview (first 4, `+N more` beyond that); the move loop then calls `moveHangarCore()` sequentially with **no print-tag prompt per vehicle** — bulk mode skips printing entirely rather than firing a confirm dialog for every car — and reports one accurate summary (`"4 vehicles moved to Hangar 19"` or `"2 vehicles moved to Hangar 19 — 1 failed"`, never claiming full success when something failed). A failed record keeps its original location and its error in `_lastBulkH19Failures` for individual retry — never a silent `.catch(()=>null)`. Refuses outright (before the confirm, before any write) when `_offlineNet` shows the device offline or Supabase unreachable.

**Audit note — pre-existing gap in `bulkMoveLoc()`:** the existing generic bulk Move Hangar (checkbox-selection based) does not call `moveHangar()`/`moveHangarCore()` — it has its own inline `sbUpdate()` loop, predating this work, with no offline-pending guard and a silent `.catch(()=>null)` that would drop a pending record from the "moved" count with no explicit message (the same shape of gap `doArchive()` had before Phase 2 fixed it). Flagged here for visibility; intentionally not touched as part of this change, per explicit scope.

Both H19 actions remain online/server-backed only — offline devices see the same "Available after synchronization" guard as every other mutation, per the Offline Mode Phase 2 architecture; neither queues through `offline_checkins`.

## TV Mode

**Purpose:** a dedicated, read-only operations board for an HDMI-connected TV that stays on ~24 hours/day at the FBO front desk, giving attendants an at-a-glance view of today's activity without needing an attendant logged into the normal app on that screen.

**Access:** `?mode=tv` (or `#tv`) on the app URL, opened via the "📺 Open TV Mode" button in the header or a direct bookmark. Requires a normal Supabase sign-in on that device (same auth as the rest of the app) — TV Mode is a display mode of the authenticated app, not a separate public page. **Strictly read-only:** the TV Mode code path (`isTvMode()`/`initTvMode()` and everything under it in `index.html`) never calls create/update/delete/delivery/print/SMS logic — it only reads `data` (via the same `sbGet()`/`mapPassengerRow()` the rest of the app uses) and renders it.

**Pages & rotation (dynamic since 2026-08-24):** 1..N pages per group — **Today**, **Tomorrow**, **Operations** — the page count is computed fresh on every render from actual data volume (`tvBuildTodayPages()`/`tvBuildTomorrowPages()`/`tvBuildOpsPages()` in `index.html`, reconciled into the DOM by `tvReconcilePageDom()`), not a fixed `3`. A quiet day still gets exactly 3 pages, same as before; a busy day gets continuation pages labeled `TODAY 2/2`/`TOMORROW 2/2`/`OPERATIONS 2/2` next to that section's count pill, only ever created when volume actually requires it. Today always keeps the longest rotation dwell (15s) even across its own continuation pages — rotation dwell is now decided by page *kind* (`_tv.pageKinds[i]`), not by assuming Today is always page index 0, since that's no longer guaranteed. Tomorrow/Operations pages dwell 12s. Manual Pause/Next controls and page-position dots are unchanged.
1. **Today** — two independently-paginated columns, **Leaving Today** and **Checked In Today** (name, vehicle+color, hangar/location, ticket, exact stored `HH:MM` departure or check-in time — see Time Format below — a flight-number line on Leaving Today rows when `return_flight` is set, a ✓ DELIVERED chip on same-day-delivered Checked-In-Today rows, a red NO LOCATION indicator on any row missing a hangar, and the Hangar 19 Welcome Back reminder chip — unchanged, see below). A busy Leaving Today with a quiet Checked In Today no longer forces both columns onto the same page count incorrectly — each paginates from its own row count.
2. **Tomorrow** — the **Leaving Tomorrow** prep view: one shared card grid per page (not one per time bucket — see High-Volume Density below), still visually grouped by time bucket header (Early Morning → After Hours) within that page's slice, exact stored `HH:MM` departure time (never 12-hour), flight number when present, and the same before-delivery-only badges as always (✈ ASCEND, NOT RETURNING — never CUSTOMS/LOCKBOX).

A compact KPI row sits above the pages on every page: Checked In Today, Leaving Today, Leaving Tomorrow, Missing Locations, **Return Follow-Up** (replaces the old Customs/Special slot — see below), and Total In Custody (all active, non-delivered records — not date-scoped).

**Time format (2026-08-24):** Leaving Today and Leaving Tomorrow show the exact stored `HH:MM` departure time — `14:30`, `07:15`, `17:00` — never converted to 12-hour (`2:30 PM`). The one conversion function that did this, `tvFmt12()`, was removed entirely (its three call sites — `tvCard()`, `tvRenderPageToday()`, the KPI row's "Next departure" sub-label — now use `getDepartureTime(r)`'s raw value directly). Missing/invalid time still shows the existing `TIME NOT SET` — never guessed. Checked-In-Today's check-in *timestamp* column is unaffected (it was never part of this request and stays 12-hour, matching how check-in time reads everywhere else in the app).

**"Checked In Today" definition:** the passenger's actual check-in timestamp, not Return Date. Primary source is `checkin_date` (an ISO timestamp written at insert time); for older records that predate that column, TV Mode uses the same `checkin_date || ts` fallback already resolved by `mapPassengerRow()` and used elsewhere (Dashboard's Arrived Today, the Operations Report). ISO values are parsed with `new Date()` and compared against the local calendar day (`sd()`/`getToday()` from `utils.js`) rather than by string-splitting, so a check-in near a local-day boundary lands on the correct day regardless of the server's UTC offset. Non-ISO legacy strings fall back to the existing `isArrToday()` parser. Sorted newest check-in first. This replaced an earlier version of TV Mode that used the legacy `ts` field only — `ts` and `checkin_date` are written at the same instant for every record since `checkin_date` was introduced, so the two only ever differed for pre-`checkin_date` legacy rows, which the fallback already covers.

**Hangar 19 Welcome Back reminder (2026-08-24):** a read-only visual reminder on Leaving Today rows for when to send the existing Hangar 19 Welcome Back SMS — TV Mode never sends it. Reuses the Dashboard's own eligibility and ETA logic exactly (`getWelcomeBackEta()`, `isValidDepTime()`, `isAscend()`, `r.delivery_type`, `r.welcome_back_sent_at` — no second interpretation of departure time): excluded entirely for Ascend (separate Customs-based workflow) and Customs deliveries, and never guessed when departure time is missing/invalid. States, driven by the shared `WELCOME_BACK_REMINDER_MINUTES` constant:
- More than the threshold before departure — no badge.
- Within the threshold through departure time, not yet sent — amber **SEND WELCOME BACK**.
- Past departure time, still not sent — red **⚠ WELCOME BACK OVERDUE** (the row's left border also turns red; this is the only red state).
- `welcome_back_sent_at` set — quiet green **✓ WELCOME BACK SENT**, regardless of timing.

No animation on any state (TV Mode's existing no-flashing rule). Recomputed once a minute by extending the existing 1-second clock tick (`updateTvClock()`) to also call `renderTvDashboard()` whenever the seconds roll to `:00` — no second timer was added, and no network call is made (re-renders against already-loaded `data`).

**`WELCOME_BACK_REMINDER_MINUTES` (shared constant, = 30):** defined once, immediately above `getWelcomeBackEta()`. Both Dashboard call sites (`welcomeBackButtonHtml()`'s initial-render urgency check, and `refreshWelcomeBackUrgency()`'s 60-second live DOM-class toggle) and TV Mode's reminder all read this single constant — changed from a hardcoded 20 minutes (duplicated in two places) to 30 minutes on 2026-08-24, specifically so Dashboard and TV Mode can never show contradictory timing again.

**"MOVE TO H19" reminder badge (2026-08-24):** a read-only pulsing amber/orange reminder on Leaving Today rows and Leaving Tomorrow cards for a vehicle that isn't physically at Hangar 19 yet — TV Mode never moves anything, it only flags it. Eligibility (`tvNeedsH19Move(r)`): `status!=='DELIVERED' && loc!=='HANGAR 19' && !isOfflinePending`. Derived purely from `r.loc` — no separate TV-only acknowledgement flag and no new database field — so the badge disappears automatically on the next TV render once Dashboard's individual Quick H19 or Bulk H19 (see Dashboard, above) successfully changes a record's location; a failed move leaves `loc` unchanged and the badge stays. Animation is a gentle opacity pulse (never fading toward 0, so it stays readable at all times) that animates only the badge itself, never the row/card — Today's badge pulses faster/stronger (`tvMoveH19PulseStrong`, 1.4s, with a soft box-shadow) than Tomorrow's (`tvMoveH19Pulse`, 1.8s, opacity only), both muted amber (`#d97a06`/`var(--tv-warning)`) — red is still reserved for genuinely critical states elsewhere in TV Mode. Both respect `prefers-reduced-motion: reduce` (animation removed entirely). **Layout — Leaving Today:** `tvRow()` gained a second, optional badge row (`opts.statusBadges`) rendered below the meta/flight lines, separate from the passenger name — the H19 badge and the Welcome Back badge (moved out of the old name-adjacent placement into this same row) now sit together there, so a long name is never at risk of being squeezed or truncated by a badge sharing its line. Every other `tvRow()` consumer (Checked-In-Today, Customs/Ascend, Return Follow-Up) is unchanged — none of them pass `statusBadges`. **Layout — Leaving Tomorrow:** uses the pre-existing `.tv-card-badges` area (`tvCard()`), concatenated after the existing Ascend/Not Returning badges (`tvBadges(r)`) — no new area was needed there.

**High-Volume Density caps retuned for the badge row (2026-08-24):** adding a badge (or two, on Leaving Today) measurably increases row/card height only on rows that actually have one — measured at 1920×1080 against the real fixed page ceiling (`.tv-list` caps at 809px, `.tv-card-grid` at 838px), worst case (every eligible row/card badged, which is realistic on a day when hangar moves haven't happened yet): `TV_ROW_CAP` `{normal:8→7, compact:9→8, high:12→8}`, `TV_CARD_CAP` `{normal:7 unchanged, compact:10→6, high:11→6}`. High tier's row cap and Tomorrow's compact/high card caps needed the largest cuts — the original caps were tuned against un-badged content and left far less margin than they appeared to (Tomorrow's card grid in particular renders as a single column at these widths, so 10-11 badged cards overflowed the true ceiling by ~480-500px even though the pre-badge baseline never showed it). Re-verified against a 1920×1080 stress dataset with every Leaving Today row carrying **both** badges simultaneously (the realistic worst case) and long names (`CHRISTOPHER ALEXANDER MARTINEZ`, `ALEXANDRIA MONTGOMERY-SMITH`, `JOHNATHAN PAUL WILLIAMS`) mixed in: zero vertical overflow and zero badge-row line-wrapping across every page at the new caps, with the same three genuinely-extreme names still the only ones affected by the pre-existing name-truncation tradeoff (no ordinary name regressed).

**Customs / Ascend panel:** tracks two things using only existing helpers — no new business rules.

Sorted by urgency: TODAY, TOMORROW, future dated returns, NO DATE last (`tvAscendSortRank()`). Each row shows a compact `RETURN:` badge (`tvReturnDateLabel()`) — `TODAY` / `TOMORROW` / the actual date (`AUG 27`) / `NO RETURN DATE` when missing — never hidden.
- **AT CUSTOMS** — unchanged from the original design, audited on 2026-08-24 and found no inconsistency worth touching: any record where `isCustomsDelivered(r)` is true, scoped to today/tomorrow by return date, not filtered by `isAscend()` (a regular Makers Air Customs delivery still appears here too). Same muted-row/name-strikethrough/GRATUITY DUE styling as before.

Because Ascend In Custody explicitly requires `status!=='DELIVERED'` and AT CUSTOMS explicitly requires `status==='DELIVERED'`, the two groups stay mutually exclusive — an Ascend vehicle moves from one to the other the instant it's actually delivered via Customs, never appearing in both.

**Return Date Follow-Up (new, 2026-08-24):** a persistent Operations column reminding the team which in-custody passengers still need their return date confirmed — not just Today/Tomorrow, and not removed just because a confirmation text was sent (sending isn't the same as the date actually being confirmed). Eligibility: active (not `DELIVERED`, not `ARCHIVED`) and either `status==='NO DATE'` or `isApproxRecord(r)` is true (the existing obs-text helper, trusted as-is — this also naturally catches an Ascend vehicle that's simultaneously NO DATE, since the two lists aren't mutually exclusive by design). Sorted by urgency: NO DATE, approx overdue, approx today, approx tomorrow, future approx (`tvFollowUpRank()`), ties broken oldest-check-in-first. Chips (`tvFollowUpChip()`): `NO DATE — FOLLOW UP` / `APPROX <date> — CONFIRM` (both amber) / `APPROX OVERDUE` (red — the only red state here, matching the rest of TV Mode's "red is reserved for genuinely critical" convention). **Audited and deliberately not built:** a "message sent" status chip — `sendReturnDateConfirmationSms()` ([index.html](index.html)) persists no timestamp/flag anywhere (unlike Welcome Back's `welcome_back_sent_at` or Customs's `customs_welcome_sent`), so there is no reliable state to show; inventing one would mean either a schema change (out of scope) or a fake client-only flag that resets on reload. The KPI row's **Return Follow-Up** tile replaces the old Customs/Special slot — the Customs gratuity-due count that used to live there is preserved as this tile's sub-label rather than dropped.

**Operations page architecture — Group A / Group B (2026-08-25):** replaced the original fixed "3-4 columns always share one page" layout after a real physical-TV photo showed Active Vehicles by Location clipped on the right edge and Return Date Follow-Up showing an internal scrollbar — neither reproduced in the original 1920×1080-only synthetic testing, only at real, narrower TV viewports. Two root causes, both fixed:
- **Horizontal clipping** — `.tv-ops-col` never set `min-width:0`, so a flex item refused to shrink below its content's intrinsic width; Alerts/Customs' long uppercase badge text (`MISSING LOCATION`, `NO DATE — FOLLOW UP`) held its own width regardless of viewport, and Active Vehicles — the *shortest*-content column — absorbed 100% of the resulting squeeze and got pushed past the page edge, clipped by `.tv-page-body{overflow:hidden}`. Fixed with `min-width:0` on `.tv-ops-col`.
- **Vertical scrollbar** — `.tv-list{overflow-y:auto}` (now `overflow:hidden` everywhere, see below) was silently absorbing whatever `TV_ROW_CAP` under-fit; the shared static `TV_ROW_CAP` (tuned for Today's wider 1-of-2-column rows) was reused for Operations' narrower 1-of-3/4-column rows, whose real per-row height differs.

**Group A** (Special Handling & Alerts, Customs/Ascend, Active Vehicles by Location) is kept on one page whenever the real measured page-body width comfortably fits all three (`tvRealPageBodyBox()` reads an already-rendered `.tv-page-body`'s live `getBoundingClientRect()` — never an assumed 1920×1080). Below that threshold it degrades to `{Alerts+Customs}` + `{Location alone, full width}` ("medium"), then to one widget per page ("narrow") — Location is never the column that gets squeezed, since measurement showed it was never actually the wide one. **Group B** (Return Date Follow-Up) no longer shares Group A's row at all — it gets its own dedicated continuation page(s), full page width, responsive 1 or 2 sub-columns depending on real measured width (mirrors Today's existing two-independently-paginated-columns pattern), and is skipped entirely when there are zero eligible records (a quiet day gets no extra page, per the low-volume requirement). `OPERATIONS i/N` labeling is computed once across the combined Group A + Group B page set, so it always reads as one continuous sequence.

**Dynamic row capacity — real measurement, not a shared static constant (2026-08-25):** `tvMeasureColumnCapacity()` renders two copies of realistic worst-case row markup (the same `tvRow()`/list-row HTML the real page uses) inside `#tvMeasureProbe` — a permanently offscreen (`position:fixed;left:-9999px;visibility:hidden`), never-interactive element in the static markup — sized to the *real* target column width and the *real* available height for that specific column (`tvMeasureElementOuterHeight()` measures the real title's rendered height, including margin, the same way), reads the row's actual `getBoundingClientRect().height`, and computes `floor((availableHeight - TV_OPS_SAFETY_MARGIN_PX + gap) / (rowHeight + gap))`. One offscreen render, one measurement, then cleared — never a loop, never touching the visible page, bounded to exactly this single operation per column per render. `TV_OPS_SAFETY_MARGIN_PX = 30` reserves headroom against browser/font/overscan variance rather than filling the container to its exact last pixel (a real-TV screenshot showed content reaching the visible edge). Falls back to the existing static `TV_ROW_CAP[tier]` only if the probe itself is unavailable or returns nothing measurable — Today/Tomorrow's own `TV_ROW_CAP`/`TV_CARD_CAP` usage is completely unchanged, this only replaces how Operations computes its own caps.

**No more scrollbar reliance, anywhere in TV Mode (2026-08-25):** `.tv-list{overflow-y:auto}` → `overflow:hidden`. TV Mode has no mouse/remote, so an interactive scroll container was never something a passive viewer could actually use — the real defense is the capacity math above; `overflow:hidden` remains only as a last-resort visual safety net if that math is ever wrong in the future, and `tvVerifyNoOverflow()` still `console.warn`s (dev-tools only) when it fires, so a regression is caught rather than silently turned into a scrollbar nobody could reach.

**v6 same-day fix — stale KPI height at capacity-measurement time (2026-08-25):** the v5 deploy above passed every pre-deploy test, but production verification (rendering a constrained synthetic scenario on the live site itself, not just checking that the new code was present) found real Operations overflow that no pre-deploy test had caught: `tvDoRender()` called `tvRenderKpis(vm)` *after* building Operations pages, so `tvBuildOpsPages()`'s real-DOM capacity measurement (`tvRealPageBodyBox()`, which reads whatever `.tv-page-body` already exists) read the **previous** render's KPI row height, not the current one. This is silently correct whenever KPI row height happens to stay the same between two consecutive renders — which is exactly what every repeated-call-on-an-already-settled-page local test exercised — and silently wrong the moment it doesn't (KPI label text can wrap depending on content, e.g. the very first render with real data after the near-empty bootstrap state, which a real device hits on every fresh load). Fixed by moving `tvRenderKpis(vm)` to run *before* the page-building calls in `tvDoRender()`, so the real available height Operations measures against always reflects the render actually in progress. Re-verified with a deliberately adversarial sequence — repeated `tvDoRender()` calls cycling Follow-Up count `5→15→30→0→30→5→20→1→15` with no reload in between, maximizing KPI-height transitions between consecutive renders — at 1920×1080, 1600×900, and 1366×768: 27/27 combinations clean (0 missing, 0 duplicate, 0 overflow, 0 clip, 0 horizontal overflow). `airvalet-shell-v6` ships this fix same-day as v5.

**v7 — adaptive fit engine for Today/Tomorrow (2026-08-25):** physical 32" TV testing found Leaving Today, Checked In Today, and Leaving Tomorrow still showing real scrollbars in production despite the v5/v6 Operations fixes — because those two page groups still relied on the static `TV_ROW_CAP`/`TV_CARD_CAP` guessing that Operations had already moved away from. This release generalizes Operations' real-DOM measurement into a genuine MEASURE → SHRINK → RE-MEASURE → PAGINATE-ONLY-IF-NECESSARY engine used everywhere:

- **`tvFitTier(classForTier, html, widthPx, availHeightPx)`** renders the real candidate content (not a generic sample) offscreen at the real target width with no height constraint, so `scrollHeight` is the true natural content height, and steps through 5 bounded density tiers — `normal → compact → high → xcompact → min` — stopping at the first one whose natural height clears the real available height (with a `TV_FIT_SAFETY_MARGIN_PX = 16` margin, not just numerically ≤ — an offscreen-probe-vs-final-render gap of ~7px was measured directly). Passenger name and departure/check-in time hold at an **11px floor** at tiers 3-4 — every further reduction after that comes from padding, gaps, secondary text (down to ~9px), and badges (down to 8px), never the name/time themselves, per the approved shrink-priority order (section spacing → row/card gaps → card padding → secondary text → badge padding, name/time last).
- **`tvFindCapacityAtTier(...)`** — only reached if even the `min` tier doesn't fit everything — a bounded binary search (`ceil(log2(count))` probe measurements, never a loop over the record count itself) for the largest number of records that actually fit at the densest tier; that becomes page 1's slice, the remainder becomes continuation page(s) via the existing `tvPaginate()`.
- **`tvBuildTodayPages()`** fits Leaving Today and Checked In Today **independently** — different volume on each side can land on a different tier, so a busy Leaving Today never forces a quiet Checked In Today down to the same density.
- **`tvBuildTomorrowPages()`** fits the shared card grid the same way; the two new tiers (`xcompact`/`min`) also use a narrower `grid-template-columns` minmax (280px/230px vs the existing 320-360px) so more columns fit per row at high density — using width to reduce height, not just shrinking cards in place.

Two confirmed CSS bugs found during the same audit, both fixed independently of the fit engine:
- **`.tv-card-grid` still had `overflow-y:auto`** — missed when `.tv-list` was switched to `overflow:hidden` for v5; this is the exact container the real physical-TV Leaving Tomorrow scrollbar was traced to.
- **A pre-existing `@media (max-width:1400px){.tv-kpi-row{grid-template-columns:repeat(3,1fr);}}` rule** forced the KPI row from 6 columns to 3 (i.e. 2 grid rows instead of 1) at exactly the width range a real TV is likely to report — measured as the dominant cause of the KPI row inflating from ~136px to ~250px and eating directly into every page's available height below it. Removed entirely — TV Mode's realistic width floor is a genuine display, never a phone, so 6 columns simply getting narrower (backed by `.tv-kpi-lbl` finally gaining `white-space:nowrap`, which `.tv-kpi-sub` already had) keeps the row short and stable instead of wrapping to extra rows or extra grid rows.

**Responsive reflow (2026-08-25):** TV Mode previously never re-rendered on viewport change at all — no `resize` listener existed. `tvHandleViewportChange()` (debounced 350ms, bound only while `tv-active`, torn down in `destroyTvMode()`) now calls `tvDoRender()` on `resize`/`fullscreenchange`/`webkitfullscreenchange`, so entering fullscreen or an actual window/TV resize re-runs the full fit-tier/pagination/KPI recalculation instead of staying frozen at whatever tier applied at load. No reload required.

**TV diagnostics (2026-08-25):** a new "📺 TV Mode Diagnostics" panel in Debug (`tvDiagRefresh()`) — `window.innerWidth`/`innerHeight`/`devicePixelRatio` (always live), fullscreen state, current page/total pages, the active page's fit tier and every generated page's tier, current page `clientWidth`×`clientHeight`/`scrollWidth`×`scrollHeight`, last `tvVerifyNoOverflow()` result, KPI row height, and page-body height. Page/fit-tier fields read from `_tv` state and the still-present `.tv-page` DOM, both of which survive `destroyTvMode()` (it only stops timers/listeners), so this shows the real numbers from the most recent TV Mode render in that browser tab — not a guess at what the real TV's viewport is. Deliberately never rendered inside TV Mode's own page, per explicit instruction not to clutter the passive display with diagnostics text.

**`tvVerifyNoOverflow()` extended (2026-08-25):** now checks, on the active page only: every `.tv-list`/`.tv-card-grid`'s `scrollHeight`≤`clientHeight` **and** `scrollWidth`≤`clientWidth` (previously height only), and every individual `.tv-row`/`.tv-card`'s own bottom/right edge against the real page-body's bounds. Still `console.warn`-only (dev-tools, never on-screen) — this is the safety net the fit engine is supposed to make unreachable, not the primary defense; result stored on `_tv.lastFitCheck` for the diagnostics panel.

**Verified (2026-08-25):** the exact realistic scenario from the physical-TV photos — 3 Leaving Today (one with both an H19-move and a Welcome-Back badge active), 4 Checked In Today, 6 Leaving Tomorrow (1 timed, 5 TIME NOT SET, H19/Ascend badges mixed in) — at 1366×768 and 1280×720: Today stays at `normal` tier (0 overflow) at both sizes; Tomorrow correctly steps down (`high` tier at 1366×768, `high` tier at 1280×720 in the final safety-margin-corrected build) with all 6 cards on one page, 0 overflow, 0 hidden cards. **TV Mode passenger-name shortening (2026-08-27):** every passenger name shown inside TV Mode is now passed through a new `tvShortName()` helper (`index.html`) before display — the first word is reduced to its initial, every remaining word is preserved exactly as stored: `MATHEUS FERIAN` → `M FERIAN`, `MATHEUS FERIAN SOARES` → `M FERIAN SOARES`, `JOHN VAN DER BERG` → `J VAN DER BERG`, a single-word name (`MATHEUS`) is left unchanged. Deliberately a dumb, deterministic split-on-whitespace rule — it never guesses which word is culturally the "real" surname, never drops middle names, and never re-cases anything beyond uppercasing the kept initial, so hyphenated and multi-word surnames (`SMITH-JONES`, `VAN DER BERG`) pass through intact. **Display-only and TV-Mode-only:** applied at TV Mode's three name-render points — `tvCard()` (Leaving Tomorrow), `tvRow()` (Leaving Today, Checked In Today, Ascend/Customs, Return Date Follow-Up), and `alertsColHtml()` (Special Handling & Alerts) — `r.name` itself is never reassigned, so Dashboard, search, SMS, printed tickets/tags, reports, activity logs, and Offline Mode all continue to show the full name exactly as before; only the string handed to `escapeHTML()` at those three TV render calls changes. Ships as `airvalet-shell-v9`.

**High-Volume Density (2026-08-24):** replaced the single global `TV_DENSITY_THRESHOLD` (one compact/normal toggle based on a combined Today+Tomorrow+CheckedIn count) with per-section adaptive tiers — `tvTierForCount()` picks `normal`/`compact`/`high` from *that section's own* row count (each Today column, the Tomorrow card group, each Ops list independently), so a busy Ops page and a quiet Today page no longer share one density decision. Sections that still don't fit at the `high` tier are paginated (`tvPaginate()`, `TV_ROW_CAP`/`TV_CARD_CAP`) rather than left in the old `overflow-y:auto` containers — TV Mode has no interaction, so content that scrolled below the fold was previously invisible to a passive viewer, not just "scrollable." The Tomorrow page was also restructured from one `.tv-card-grid` **per time bucket** to one shared grid **per page** (bucket headers as full-width grid items within it) — per-bucket grids were measured splitting the page's available height unevenly, overflowing several small buckets even when the page as a whole had room. Cap values (rows/cards per page per tier) are grounded in real pixel measurements taken against this layout at 1920×1080, tuned iteratively against a 101-record synthetic stress dataset until a direct DOM assertion (`scrollHeight` vs `clientHeight` on every `.tv-list`/`.tv-card-grid`, cycled across every page) showed zero overflow — not guessed. `tvVerifyNoOverflow()` re-runs that same check on every render and page transition and `console.warn`s (dev-tools only, never on-screen) if a future layout or content change breaks the estimate, so a regression is caught rather than silently accepted. Long names are protected in priority order: full name preserved whenever possible (Tomorrow's card columns were widened from 260px to 360px minimum specifically because 260px was measured truncating 18 of 24 names — including short ones — under volume at full 1920×1080), then tier-based font/padding reduction, with `text-overflow:ellipsis` as the last-resort fallback (verified on the genuinely extreme test names — `CHRISTOPHER ALEXANDER MARTINEZ`, `ALEXANDRIA MONTGOMERY-SMITH` — that even truncated, 60-75% of the name stays visible, enough to identify the passenger). Names are never wrapped into multiple lines. Tested at 1920×1080 (primary) and 3840×2160 — confirmed via computed-geometry assertion that containers/rows scale to fill the viewport with zero overflow at 4K as well; a visual screenshot at that resolution could not be reliably captured in this environment (a tool-side limitation, not a rendering bug — the DOM measurements are unambiguous).

**Reliability:** Supabase realtime subscription (best-effort, debounced 800ms) layered over a 60s reconciliation poll that alone guarantees the board is never more than ~60s stale; a 15s watchdog that forces an extra reconciliation past 90s without a successful update and shows a STALE DATA banner past 180s; exponential-backoff realtime reconnect; local-clock-only date-rollover detection (no server round-trip) that re-renders Today/Tomorrow groupings and forces a reconciliation at midnight; a session-expired overlay if the Supabase token is rejected (401/JWT error); fullscreen support; cursor auto-hide and an auto-hiding corner control panel (Full Screen, Refresh Now, Pause/Resume Rotation, Next Page, Copy TV URL, Exit TV Mode); and full teardown (`destroyTvMode()`) of every interval/listener/realtime channel on exit or `beforeunload`, so nothing leaks if the tab is reused.

## Offline Mode

**Status: Phase 2 (real emergency Offline Check-In) — implemented 2026-08-24, tested on desktop only, NOT YET deployed.** `saveEntry()` now has a real offline branch: on a known-offline device (or a genuine network-level failure of the online attempt), a new check-in is written to IndexedDB first and only counted as saved once that write is confirmed — see "Phase 2 — real Offline Check-In" below for the full mechanics. Online New Entry's own code path is byte-for-byte what it was before this phase; nothing about a normal, connected check-in changed.

**Full design:** a 22-point audit and architecture report, followed by a focused follow-up on ticket format/device identity/auth window, preceded implementation — see this repository's development history for the complete reasoning (ticket collision analysis, idempotency strategy, sync state machine, RLS/RPC considerations, iPad/Safari-specific risk analysis, etc.). Summarized here is only what Phase 1 actually built.

**Files added:** `service-worker.js`, `offline-db.js`, `offline-auth.js`, `vendor/supabase.js`. **Modified:** `index.html` only (script tags, header connectivity indicator, update banner, Debug-tab diagnostics panel, `onAuthStateChange` hook). `styles.css` required no changes — the diagnostics panel reuses the existing `.epson-card`/`.epson-stat-grid`/`.epson-btn` component classes already established for the Printer Diagnostics section.

**Service worker & app shell:** `service-worker.js`, registered with relative scope (`./service-worker.js`) so it works correctly under GitHub Pages' `/farber-parking/` path without hardcoding it. Precaches exactly 8 files into a versioned cache — `./`, `./index.html`, `./styles.css`, `./utils.js`, `./logo.PNG`, `./vendor/supabase.js`, `./offline-auth.js`, `./offline-db.js` — via `cache.addAll()`, which is atomic: any single failed/non-2xx request fails the entire install, so a service worker can never claim offline-readiness with a partially-cached shell. The fetch handler is an explicit allow-list — only requests matching one of those 8 files are ever served from cache; everything else (Supabase REST/Auth/RPC, any other origin) passes straight through untouched, always network-only. `activate()` deletes any `airvalet-shell-*` cache that isn't the current version. New workers never auto-activate or force a reload mid-session — they sit in `waiting` until the attendant taps "Reload Now" on the Update Available banner, which posts `{type:'SKIP_WAITING'}` to the waiting worker; a single `controllerchange`-triggered reload follows (not a loop). To bump the shell version on a future deploy, change `CACHE_VERSION` in `service-worker.js`.

**Cache version history:** `airvalet-shell-v1` (Phase 1, 2026-08-24) → `airvalet-shell-v2` (2026-08-24, deployed — Offline Mode Phase 2 + the first TV Mode/Quick H19 release) → `airvalet-shell-v3` (2026-08-24, deployed — Quick H19 relocated into the quick-action row + Bulk H19 added) → **`airvalet-shell-v4`** (2026-08-24, not yet deployed) — bumped because Quick H19 visibility was scoped to Leaving Today/Tomorrow only (previously shown on every Dashboard section) and the Leaving Today header's `Print All`/`All H19` buttons were regrouped to fix a layout bug; the TV Mode "MOVE TO H19" reminder badge and its High-Volume Density cap retuning (see TV Mode, above) shipped in this same v4 package rather than triggering a v5. `SHELL_FILES` unchanged across all four versions — the same 8 files, re-verified each time by grepping every local `src`/`href` in `index.html` for anything new (nothing was ever added).

Every upgrade path so far (v1→v2, v2→v3, and now v3→v4) was simulated end-to-end against a genuinely separate origin state before being considered safe to ship, same methodology each time: install the *old* version fresh, set real `deviceId`/`deviceCode='M1'`/offline-auth marker/IndexedDB state (v3→v4 additionally seeded one real `LOCAL_PENDING` offline check-in record), then swap in the new version's files and reload — confirming the new worker installs in the background while the old one keeps serving the active page (checked via function-presence/constant-value, e.g. `TV_ROW_CAP.normal` staying at the old version's value until acceptance), the "Update Available — Reload Now" banner appears, `offlineApplyUpdate()` → `skipWaiting()` → one `controllerchange` reload hands control to the new version, the old cache is actually removed (`caches.keys()`), IndexedDB/device identity/offline-auth/the pending check-in record all read back byte-identical afterward (still `LOCAL_PENDING`, not auto-synced), and a cold launch with the dev server stopped entirely still loads the full app from cache with zero console errors.

**Vendored Supabase JS:** was `cdn.jsdelivr.net/npm/@supabase/supabase-js@2` — a **floating major-version tag**, not a true pin (jsdelivr resolves `@2` to whatever the latest 2.x release is at request time). Resolved and frozen at exactly **2.112.4** on 2026-08-24, fetched from `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2.112.4/dist/umd/supabase.js` and committed unmodified as `vendor/supabase.js` (SHA-256 `f8ce7fab799af1916019cbd0b485b39bb80dbdbc6dc062909a751c9e5198e04c`). This removes the CDN as a hard dependency for the app to even load, and means the library version can no longer drift silently — a future upgrade must be a deliberate, visible change to this file.

**Connectivity detection:** a header indicator (🟢 ONLINE / 🟡 NETWORK — NO SERVER / 🔴 OFFLINE) driven by two independent signals that are never conflated: `navigator.onLine` (device network interface only) and a real, rate-limited reachability probe (`offlineProbeSupabase()`, a lightweight `GET .../rest/v1/passengers?select=id&limit=1`, minimum 15s between checks, triggered on `online` events and on the tab becoming visible again — never polled aggressively). `navigator.onLine===true` is never treated as proof Supabase is reachable.

**Device identity:** `getOfflineDeviceId()` — a `crypto.randomUUID()` generated once and stored in `localStorage`, stable across reloads and across changing the device code, never shown to attendants. `getOfflineDeviceCode()`/`setOfflineDeviceCode()` — a short, human-facing code (e.g. `M1`), **manually assigned only, never auto-generated** (two iPads must never silently receive the same code). Validated to 1-4 uppercase letters/digits starting with a letter, and explicitly rejects `A` or anything starting with `A-`, to stay unambiguous with the Ascend ticket rule. **Not yet enforced unique across devices** — Phase 1 has no server-side registry; a `devices` table with a `UNIQUE(device_code)` constraint is required before Offline Check-In can be safely enabled (Phase 3, alongside the sync migration below).

**Offline authorization window:** `OFFLINE_AUTH_WINDOW_HOURS = 24`, a single named constant. On every `SIGNED_IN`/`TOKEN_REFRESHED` event, `recordOfflineAuthSuccess(email)` writes `{deviceId, userEmail, lastAuthenticatedAt, expiresAt}` to `localStorage` — timestamp/email/device id only, **never** a password, JWT, or refresh/access token. `SIGNED_OUT` deliberately does not touch this marker — it neither refreshes nor clears it; it only ever expires on its own schedule. This marker is **not** a Supabase session and does not prove Supabase would authenticate the user right now — while offline, that can't be verified at all. It means exactly: *this operational iPad successfully authenticated online within the last 24 hours.* Once Offline Check-In exists (Phase 2+), a valid window permits it; an expired or missing window shows "OFFLINE ACCESS NOT AVAILABLE — connect to the internet and sign in," and already-queued records are never deleted because this window expired.

**IndexedDB (`airvalet_offline`, version 2):** two object stores. `offline_checkins` (keyPath `offline_sync_id`, indexed on `syncState`/`createdAt`) — unchanged shape from Phase 1 (`offline_sync_id`, `payload`, `createdAt`, `syncState`, `serverPassengerId`, `attemptCount`, `lastAttemptAt`, `lastError`, `deviceId`), plus two Phase 2 fields: `isOfflinePending:true` and `deviceCode`. `server_snapshot` (new in v2, out-of-line fixed key `'current'`) — the passenger list from the last successful `loadData()`, written only after `sbGet()` actually succeeds, read only as a fallback when `sbGet()` fails (cold offline launch) so ticket-number math and the dashboard have a real starting point instead of an empty list; never written on a failed load, never touched by the offline save path.

**Ticket format is unchanged, permanently — course-corrected from Phase 1's plan.** Phase 1 had approved a device-suffix format (`MMDD-N-<DeviceCode>`); given the real operating environment (one primary iPad, one iPhone backup, offline is a rare emergency fallback, not routine multi-device simultaneous operation), that was **rejected** before Phase 2 implementation in favor of keeping the visible ticket exactly `MMDD-N` / `A-MMDD-N` forever — no device markers, no ticket-parser changes anywhere (`dcParseTicketSeq()`, the Arrived Today sort, etc. are all untouched and don't need to be). `getNextTicket()`/`getSharedDailyMax()` ([index.html](index.html), "TICKET AUTO-SUGGEST") are **completely unmodified** — the offline queue simply merges pending local records into the in-memory `data` array (see `mapOfflinePendingRow()`/`loadPendingOfflineRows()`), so those two functions keep computing the correct next ticket without knowing anything special happened. Worked example: cached snapshot max `0824-5` + one local pending `0824-6` → next suggested offline ticket is `0824-7`.

**Cross-device ticket collision is possible and is deliberately not hidden.** If the offline iPad and another device (or the online iPad after reconnecting) independently generate the same ticket number, this design does not prevent it and does not silently renumber or merge either record. Detecting and surfacing that (`TICKET CONFLICT — MANAGER REVIEW REQUIRED`, with a manager-facing comparison of both records) is explicitly **Phase 3** scope — not built yet. `offline_sync_id` (UUID) is a separate concern: it protects against a duplicate *sync* of the same offline record (retry-safe), it does **not** guarantee ticket-number uniqueness across two independently-operating devices.

**Phase 2 — real Offline Check-In:** `saveEntry()` decides its path upfront from the connectivity indicator (`_offlineNet.deviceOnline`/`supabaseReachable`, never guessed) and additionally falls back mid-attempt if the online `sbInsert()` call itself throws `TypeError` (a genuine network-level failure, as opposed to a real server-side rejection, which still surfaces as a normal error and never goes to the offline queue). The offline branch: (1) refuses outright — before touching IndexedDB — if `getOfflineAuthStatus().valid` is false or no device code is configured, showing `OFFLINE ACCESS NOT AVAILABLE — CONNECT TO INTERNET AND SIGN IN` / `...DEVICE CODE NOT CONFIGURED`; (2) builds the record (`offlineBuildCheckinRecord()`) and writes it to IndexedDB — **a rejected write is never reported as a save**: the form is left exactly as typed and the toast reads `CHECK-IN NOT SAVED — <reason>`; (3) only once IndexedDB confirms the write does this count as saved — the record is merged into `data` (`mapOfflinePendingRow()`), the form clears, and the toast reads `OFFLINE MODE — Saved locally as PENDING SYNC (Ticket <N>)`, combined with `SMS NOT COMPLETED — OFFLINE` in the same toast if a text was requested (native SMS composition is never attempted while offline in Phase 2 — no Twilio queueing either); (4) printing (if requested) happens only after that IndexedDB confirmation, using the normal ticket number, and a printing failure never rolls back or un-saves the passenger.

**Local passenger identity:** a pending record never gets a fabricated Supabase id. `offlineLocalIdFromSyncId()` (`offline-db.js`) derives a small, deterministic **negative** integer from `offline_sync_id` — negative so it can never collide with a real (always-positive) Supabase `bigint` id, and a plain number (not a UUID string) so it drops safely into the existing `onclick="fn(123)"`-style numeric attributes used throughout card rendering. `isOfflinePendingId(id)` is the shared predicate (`id < 0`).

**Guarding every server mutation against a pending record — audited exhaustively, not guessed.** Two layers: (1) a **centralized guard** inside `sbUpdate()`, `sbDelete()`, `changePassengerReturnDate()`, and `deletePassengerWithLog()` — chosen as the choke points because between them they cover every write path in the app, including the two RPC calls that bypass `sbUpdate()` entirely (`change_passenger_return_date_with_reason`, `delete_passenger_with_log` — found only by reading every call site, since a guard in `sbUpdate()` alone would have missed them). Each throws `Error("Available after synchronization.")` for a pending id. (2) **UX-layer pre-checks** at the actual entry points — `openTipModal` (the single choke point for Deliver/Customs/Lockbox, since it's where the modal opens before any mutation), `deliverWithTip`, `markDel`, `undoDeliverToday`, `moveHangar`, `changeDate`, `changeArrDate`, `deleteRec`, `saveEdits` (inline editing), `sendWelcomeBackSms`/`undoWelcomeBackSms`, and all five Customs communication functions — so a pending record shows the friendly message immediately instead of an optimistic-UI flash-then-rollback. `doArchive()` (bulk) explicitly separates pending records out and reports them as skipped in the result toast, rather than letting them disappear silently into its existing `.catch(...return null)` failure bucket.

**Reconnection never auto-uploads.** `loadData()` always re-merges local pending rows back into `data` after a successful `sbGet()` (via `loadPendingOfflineRows()`), so they survive a reload and a real reconnection exactly as `PENDING SYNC` — no code path in Phase 2 marks a record synced, deletes it, or sends it to the server; that upload step is Phase 3. `offlineProbeSupabase()` triggers one `loadData()` call on an actual reachability transition (not just the browser `online` event, which only proves a network interface is up) to refresh live server data without touching the offline queue. The header banner (`updateOfflineModeBanner()`) reflects state at all times: `OFFLINE MODE — New check-ins are saved locally as PENDING SYNC` while offline (or the ACCESS NOT AVAILABLE variant if unauthorized), `ONLINE — X CHECK-INS PENDING SERVER SYNC` once back online with unsynced local records, hidden otherwise.

**Debug tab:** now two panels. **Pending Sync** (new, real, non-diagnostic) lists every actual pending offline check-in on this device (ticket/name/vehicle/saved time/device code) with an explicit "Server synchronization is not enabled yet" notice — no Delete, no fake Sync Now, no way to mark anything synced from this screen. **Offline Mode Diagnostics** (existing, Phase 1) is now explicitly scoped to synthetic test records only — its "Clear Test Records" button was fixed in Phase 2 to filter out `isOfflinePending` records so it can never delete a real pending check-in.

**Explicitly out of scope for Phase 2 (unchanged from the Phase 0/1 plan):** the `offline_sync_id` Supabase migration, the `sync_offline_checkin()` RPC, the RLS/RPC security audit that must precede writing it, automatic upload on reconnect, and the `TICKET CONFLICT — MANAGER REVIEW REQUIRED` UI — all Phase 3.

**Tested on desktop only** (this browser's local dev server against production Supabase, with `sbInsert`/`sbGet` monkey-patched during tests that could otherwise have written real rows or required production credentials this environment doesn't have) — covering the full save order, all connectivity-decision branches, every guard, reconnection merge, and the Archive/diagnostics fixes above. **Not yet tested:** on the real iPad ("M1"), on the real Epson printer with the network actually disconnected, or with a genuine multi-hour real-world offline period. See the Changelog entry below for the exact iPad test procedure to run before this is considered field-ready.

## User Workflow

**Check-in → custody → delivery/archive**, end to end:

1. **Check-in:** `+ New Entry` → fill Name (autocomplete against history), Phone, auto-suggested Ticket, Return Date (or `NO DATE` + estimate), Vehicle, Color, Hangar. System surfaces frequent-passenger history and Early Return warnings inline.
2. **Save + Print + Text** (recommended): persists the record, prints Customer/Key/Dashboard copies, opens the Welcome SMS.
3. Attendant hands Customer Copy to passenger, clips Key Copy to keys, places Dashboard Copy in the vehicle, parks in the selected hangar.
4. **In custody:** location changes go through "Move Hangar" (single or bulk), which prompts to reprint the Key Copy — the old tag must be physically swapped, never left doubled-up.
5. **Approaching return:** Dashboard surfaces the record under Leaving Today/Tomorrow/Sunday; flight info can be attached for Flight Tag printing; Tasks tab handles unresolved date confirmations.
6. **Delivery (check-out):** locate by name/ticket → confirm identity against the physical ticket → retrieve vehicle → mark delivered → choose delivery type (Normal/Customs/Lockbox) → rate the passenger. For Customs, the Welcome Back → Gratuity SMS sequence follows.
7. **Early Return** short-circuits steps 5–6 if the passenger arrives before their scheduled date.
8. **Archive:** at period end or supervisor request, selected `DELIVERED`/stale records are archived (3-step confirm), removing them from default views but retaining full history.
9. **Daily Closing:** end of shift, reconcile cash/card/digital totals, log attendants and money pickups, check both verification boxes, and Finalize (irreversible) — or leave as Draft to revisit.

## Development Decisions

Document new entries here as **Date / Reason / Decision / Impact** whenever an architectural choice is made. Seeded from what's inferable in the current codebase:

- **Date:** 2026-07-12 (approx., per migration filenames)
  **Reason:** Need to track Customs Welcome-Back/Gratuity SMS state per trip without introducing PII into a new table.
  **Decision:** Added five nullable/defaulted boolean+timestamp columns directly onto `passengers` rather than a new join table, since each check-in is already its own row and the flags are trip-scoped by nature.
  **Impact:** Simpler queries, no joins; but any future multi-trip aggregation of Customs comms would need to scan across rows by phone/name rather than a foreign key.

- **Date:** 2026-07-12 (approx.)
  **Reason:** Daily cash/attendant reconciliation needed a system of record separate from passenger data, with a hard guarantee that finalized closings can't be silently altered.
  **Decision:** New `daily_closing_reports` table, one row per date, with a DB-level trigger blocking `FINALIZED → DRAFT` transitions (not just an app-level check) and no delete policy at all.
  **Impact:** Finalized daily closings are tamper-resistant even against direct SQL access; drafts remain fully editable until finalized.

- **Date:** unknown (pre-dates tracked migrations)
  **Reason:** Distinguish the private-flight "Ascend Valet" service from standard Makers Air check-ins without a schema change.
  **Decision:** Overload the existing `ticket` field — any ticket prefixed `A-` is treated as Ascend everywhere in the UI (`isAscend()`), rather than adding a `brand`/`service_type` column.
  **Impact:** Zero migration cost, but brand identity is now implicitly encoded in a string pattern; renaming the ticket format would silently break brand detection.
